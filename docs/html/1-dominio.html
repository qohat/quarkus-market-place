Módulo 1 · el dominio

Que el compilador haga el trabajo

Un dominio sin una sola anotación de framework, donde añadir un caso nuevo rompe el build exactamente en los sitios que hay que tocar.

El marketplace es híbrido, y eso decide todo

Vende productos físicos, cuyo recurso escaso es un contador de unidades, y servicios reservables, cuyo recurso escaso es el tiempo de un calendario.

Son dos problemas de concurrencia distintos que exigen dos respuestas distintas. Por eso el dominio se eligió así: para que los módulos 6 y 7 tuvieran algo de verdad que resolver. 

public sealed interface Listing
        permits ProductListing, ServiceListing {

    ListingId id();
    SellerId sellerId();
    Money price();
    ListingStatus status();
    Listing withStatus(ListingStatus nuevo);

    // unidades o plazas disponibles, según el tipo
    int availableUnits();

    default boolean acceptsOrders() {
        return status() == PUBLISHED && availableUnits() > 0;
    }
}

sealed declara: estos son todos los casos que existen. No es documentación — es una promesa que el compilador verifica y usa.

Qué compra esa promesa

Un switch sobre un tipo sellado no necesita default, y ahí está la ganancia. Prueba a añadir un tipo nuevo: 

public static FulfillmentCheck check(Listing listing, int cantidad) {
    return switch (listing) {
        case ProductListing p -> comprobarStock(p, cantidad);
        case ServiceListing s -> comprobarPlazas(s, cantidad);
    };  // sin default: el compilador sabe que no faltan casos
}
Dos casos, dos ramas. El switch es exhaustivo.

Con default —o con una jerarquía abierta— el código habría compilado y el caso nuevo habría caído silenciosamente en la rama por defecto. El bug se descubre en producción en vez de en el build.

ADT: el resultado lleva su motivo

Una comprobación de disponibilidad puede fallar por dos razones distintas, y el que llama necesita saber cuál. Un boolean pierde esa información; un tipo algebraico la conserva.

Con booleano

boolean puedeAtender(...)

¿No hay stock? ¿Está pausada? ¿Cuántas quedan? Hace falta otra llamada para saberlo.

Con ADT

sealed interface FulfillmentCheck

Cada resultado trae sus propios datos, y el compilador obliga a tratarlos todos.

public sealed interface FulfillmentCheck {
    record Fulfillable(Money total) implements FulfillmentCheck {}
    record NotAcceptingOrders(ListingStatus estado) implements FulfillmentCheck {}
    record InsufficientAvailability(int pedidas, int disponibles) implements FulfillmentCheck {}
}

// y en el borde REST, con record patterns:
return switch (check) {
    case Fulfillable(var total) -> ok(total);
    case NotAcceptingOrders(var estado) -> conflicto(estado);
    case InsufficientAvailability(var p, var d) -> faltanUnidades(p, d);
};

El bug de BigDecimal que casi nadie ve venir

BigDecimal.equals compara también la escala. Dos importes idénticos con distinto número de decimales no son iguales, y eso rompe equals, hashCode, mapas, conjuntos y tests, de forma intermitente. 

public record Money(BigDecimal amount, Currency currency) {

    public Money {   // constructor compacto: TODAS las construcciones pasan por aquí
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        amount = amount.setScale(currency.getDefaultFractionDigits(),
                                 RoundingMode.UNNECESSARY);
    }
}

Normalizar la escala

Todos los importes en euros tienen dos decimales. Siempre. Y así equals vuelve a significar lo que uno espera.

RoundingMode.UNNECESSARY

Lanza si haría falta redondear. Fallar antes que redondear dinero en silencio.

Y el constructor compacto

Es el único punto por el que pasa toda construcción, incluida la que haga un adaptador al leer de la base de datos.

Cero framework, tests en milisegundos

En todo el paquete domain no hay una anotación de Hibernate, ni de Jackson, ni de JAX-RS. La consecuencia práctica es que sus tests se ejecutan con new y assertions, sin levantar nada.
