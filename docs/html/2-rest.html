Módulo 2 · el borde HTTP

Dos capas de validación que no se mezclan

Bean Validation comprueba la forma del payload. El dominio garantiza los invariantes. Confundirlas duplica reglas o deja huecos.

Los recursos REST son singleton

En Quarkus REST, a diferencia de JAX-RS clásico, se instancia uno solo y lo comparten todas las peticiones. Ahorra una asignación por petición y trae una regla innegociable:

Nada de estado mutable en campos. Nunca.

ScopeVidaCuándo
@ApplicationScopedUna instancia, con proxyEl 90 % de los casos
@SingletonUna instancia, sin proxyCuando el proxy estorba
@RequestScopedUna por peticiónContexto del que llama
@DependentUna por punto de inyecciónObjetos pequeños sin estado
@SessionScopedUna por sesión HTTPNunca, si quieres escalar horizontalmente

El client proxy es lo que permite inyectar algo de vida corta dentro de algo de vida larga. Por eso UriInfo y JsonWebToken se pueden inyectar en un recurso singleton: lo inyectado es un proxy que resuelve la petición en curso.

Bean Validation — la forma

@Pattern("[A-Z]{3}") comprueba que son tres letras mayúsculas. Da un 400 con un mensaje claro y todas las infracciones a la vez.

El dominio — el invariante

Que "XYZ" no exista en ISO 4217 solo lo sabe Currency. Y esa garantía vale para cualquier vía de entrada, no solo HTTP.

No es duplicar una regla: el borde da un buen mensaje y el dominio da la garantía. Si mañana entra un consumidor de Kafka, se salta Bean Validation pero no puede saltarse Money.

DTOs separados, y por qué no es ceremonia

public record CreateProductRequest(
        @NotBlank String title,
        @Pattern(regexp = "\\d+\\.\\d{2}") String amount,
        @Pattern(regexp = "[A-Z]{3}") String currency,
        @PositiveOrZero int stock) {
    // NO hay campo sellerId. Y esa ausencia es la característica.
}

Si el cliente pudiera elegir el sellerId, cualquiera publicaría en nombre de otro. En el módulo 2 llegaba provisionalmente por una cabecera; en el módulo 5 pasó a salir del token, que es el único sitio del que puede salir.

Y el importe viaja como cadena

// JSON con número:
{ "amount": 25.00 }   →   JSON.parse   →   25      ← se perdió el céntimo
// JSON con cadena:
{ "amount": "25.00" }  →  JSON.parse  →  "25.00"   ← intacto

JavaScript convierte los números JSON a double. Para dinero eso significa perder la escala y, en importes grandes, precisión.

Errores con la misma forma: RFC 7807

Todos los fallos de la API responden application/problem+json con la misma estructura, venga de donde venga el error. 

{
  "type":     "https://marketplace/problems/not-the-owner",
  "title":    "Not the owner",
  "status":   403,
  "detail":   "This listing belongs to another seller",
  "instance": "/listings/a6f0.../archive"
}

Las excepciones del dominio no saben nada de HTTP. Cada adaptador decide qué significan en su protocolo: el consumidor de Kafka del módulo 7 trata la misma excepción como «mensaje a descartar», sin que ninguna decisión contamine a la otra.

El fallo que enseñó dónde va @Consumes

Seis tests en rojo con 415 Unsupported Media Type

Expected status code <200> but was <415>

@Consumes(APPLICATION_JSON) estaba a nivel de clase, así que se aplicaba también a publish, pause y archive — que son POST sin cuerpo y llegan sin Content-Type.

@Consumes describe lo que acepta un método, no una política de clase. Va solo donde hay cuerpo que leer. @Produces sí puede ir en la clase.
